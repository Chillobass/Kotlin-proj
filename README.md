# TenderHub - сервер площадки закрытых тендеров

Заказчик публикует тендер, администратор его модерирует, исполнители подают закрытые заявки, а в момент дедлайна сервер сам считает рейтинг и публикует итоги. Полное описание бизнес-правил - в [docs/business-rules.md](docs/business-rules.md).

**Стек:** Kotlin 2.0, Spring Boot 3.4 (Web MVC, Security, JDBC), PostgreSQL 16, Flyway, Docker Compose. Тесты: JUnit 5, Testcontainers

---

## Запуск

// Нужен только Docker

```bash
cp .env.example .env
docker compose up --build
```

- API: `http://localhost:8080/api/v1`
- Swagger UI: `http://localhost:8080/swagger-ui.html` (кнопка *Authorize* -> логин/пароль)
- Health: `http://localhost:8080/actuator/health`

При первом старте Flyway создаёт схему, а из переменных `ADMIN_EMAIL`/`ADMIN_PASSWORD` создаётся администратор. Через регистрацию можно стать только обычным пользователем.

> **Быстрая ручная проверка.** По правилам дедлайн - не раньше чем через 24 часа, поэтому дожидаться закрытия долго. Для демо поставьте в `.env` `TENDER_MIN_DEADLINE_OFFSET=2m` и `TENDER_MIN_OPEN_DURATION=1m`: тендер с дедлайном через 3 минуты закроется сам (планировщик проверяет раз в 10 с). Можно и не ждать планировщика: `POST /api/v1/admin/tenders/close-expired` закрывает все просроченные тендеры сразу.

### Локально без Docker для приложения

```bash
docker compose up -d db
DB_PASSWORD=... ADMIN_EMAIL=admin@tenderhub.local ADMIN_PASSWORD=... ./gradlew :app:bootRun
```

### Тесты

```bash
./gradlew test
```

Юнит-тесты бизнес-логики работают без внешних зависимостей. Интеграционные тесты (`*IT`) поднимают PostgreSQL в Docker через Testcontainers; если Docker недоступен, они пропускаются.

## Реализованные возможности

| Область | Что сделано |
|---|---|
| Пользователи | Регистрация, HTTP Basic аутентификация, профиль, администратор из конфигурации, блокировка и разблокировка |
| Тендеры | Создание (сразу на модерацию), редактирование и повторная отправка после отклонения, отмена владельцем, каталог с фильтрами и поиском, «мои тендеры» |
| Модерация | Очередь, одобрение (с проверкой оставшегося времени), отклонение с причиной, принудительная отмена |
| Заявки | Подача с автоматической валидацией; поданная заявка окончательна (без изменения и отзыва); «мои заявки» |
| Закрытие и рейтинг | Планировщик закрывает тендеры в дедлайн, считает взвешенный рейтинг и фиксирует места. Итог `COMPLETED` или `FAILED` (без заявок) |
| Видимость | До закрытия чужие заявки и рейтинг не видит никто, включая владельца и админа; публично только количество заявок |
| Уведомления | Админам - о новом тендере на модерации; владельцу - об одобрении, отклонении, отмене и итогах; участникам - об отмене тендера и о занятом месте |
| Блокировка | Тендеры заблокированного отменяются, его активные заявки отзываются. Смотреть площадку он может, действовать - нет |

Не реализовано (вне рамок этапа): клиент, вложения, оплата, переторжка.

## Архитектура: модульный монолит

```
common ─┬─ users ─┬─ tenders ─┬─ bidding ─┬─ notifications
        │         │           │           │
        └─────────┴───────────┴───────────┴─ app (сборка: Spring Boot, security, ошибки, транзакции)
```

Каждый бизнес-модуль - отдельный Gradle-подпроект с одинаковой структурой:

| Пакет | Содержимое | Зависимости |
|---|---|---|
| `domain` | Сущности и правила: `Tender` (state machine), `Bid`, `RatingCalculator`, `TenderPolicy` | только Kotlin |
| `application` | Сценарии (сервисы) и **порты** - интерфейсы репозиториев | domain, `common` |
| `api` | Публичный контракт модуля для других модулей: интерфейсы запросов и доменные события | domain |
| `adapter.persistence` | JDBC-реализации портов | Spring JDBC |
| `adapter.web` | REST-контроллеры и DTO | Spring Web |
| `adapter.config` | Связывание модуля в Spring-контекст и слушатели событий других модулей | Spring |

Принятые решения:

- **Бизнес-логика не знает о фреймворке.** Сервисы - обычные классы, создаются в `*ModuleConfig`. Транзакции идут через порт `TransactionRunner`, события - через `EventPublisher`, время - через `java.time.Clock`. Контроллер получает `Actor` (кто действует), а не объекты Spring Security. Проверяет это `ArchitectureTest` на ArchUnit.
- **API заменяем.** Контроллеры тонкие: DTO -> вызов сервиса -> DTO. Чтобы добавить gRPC или GraphQL, достаточно нового адаптера рядом, сервисы не меняются.
- **Хранилище заменяемо.** Сервисы зависят от портов (`TenderRepository`, `BidRepository`, …), а не от JDBC. Модули обращаются к таблицам друг друга только через публичные API.
- **Модули общаются через `api` и события.** Например, `bidding` берёт снимок тендера у `TenderCatalog`. `tenders` узнаёт количество заявок через порт `BidStatistics`, который реализует `bidding` (инверсия зависимости, без циклов). Блокировка пользователя публикует `UserBlocked`, и на него реагируют `tenders` и `bidding`. Уведомления строятся только на событиях. События доставляются синхронно в той же транзакции: уведомление сохраняется тогда и только тогда, когда закоммичено бизнес-изменение.
- **Ошибки.** Бизнес-код бросает типизированные исключения со стабильным `code`. `GlobalExceptionHandler` превращает их в RFC 7807 problem details:

  | Исключение | HTTP | Пример `code` |
  |---|---|---|
  | `ValidationException`, ошибки Bean Validation, битый JSON | 400 | `VALIDATION_FAILED`, `INVALID_EMAIL` |
  | нет аутентификации | 401 | `UNAUTHORIZED` |
  | `ForbiddenException` | 403 | `OWN_TENDER`, `USER_BLOCKED` |
  | `NotFoundException` (в том числе «не видно этому пользователю») | 404 | `TENDER_NOT_FOUND` |
  | `ConflictException` (состояние не позволяет) | 409 | `TENDER_NOT_OPEN`, `BID_ALREADY_EXISTS` |
  | `BusinessRuleException` | 422 | `PRICE_ABOVE_MAX`, `TENDER_HAS_BIDS` |

### Транзакции и конкурентность

| Ситуация | Решение |
|---|---|
| Две одновременные заявки одного участника | Частичный уникальный индекс `(tender_id, participant_id) WHERE status = 'ACTIVE'`; нарушение превращается в `409 BID_ALREADY_EXISTS` |
| Заявка в момент закрытия или отмены тендера | Подача заявки берёт `SELECT … FOR SHARE` на строку тендера, закрытие и отмена - `FOR UPDATE`. Заявки разных участников не мешают друг другу, но закрытие ждёт незавершённые заявки, а заявка после закрытия видит новый статус |
| «Владелец может отменить, только пока нет заявок» | Проверка количества заявок идёт под эксклюзивной блокировкой тендера, поэтому заявка не может «проскочить» между проверкой и отменой |
| Несколько инстансов приложения | Закрытие берёт тендер через `FOR UPDATE SKIP LOCKED`: каждый тендер закрывается ровно один раз, каждый в своей транзакции |
| Потерянные обновления | Оптимистическая блокировка: колонка `version` у тендеров и заявок, `UPDATE … WHERE version = ?` |
| Дедлок | Порядок блокировок всегда тендер -> заявка |

Инварианты дублируются в схеме: `CHECK` на сумму весов 100, `OPEN ⇒ published_at`, `closed_at` только у закрытых, уникальность мест в рейтинге.

### Конфигурация и логирование

Всё окружение берётся из переменных среды (`application.yml`, `.env.example`), секретов в коде нет. Бизнес-лимиты тоже вынесены в конфиг: `tenderhub.tender.*` (срок дедлайна, время на модерацию, лимит тендеров на модерации) и `tenderhub.closing.*` (планировщик).

Каждый запрос получает `X-Request-Id`; он попадает в MDC и в каждую строку лога. Логируются access-строка на каждый запрос API, бизнес-события (тендер одобрен, заявка подана, тендер закрыт), ошибки планировщика и необработанные исключения.

## API (кратко)

Все запросы, кроме регистрации, требуют HTTP Basic (`email:password`).

| Метод и путь | Кто | Что |
|---|---|---|
| `POST /api/v1/auth/register` | все | Регистрация |
| `GET /api/v1/users/me` | все | Профиль |
| `POST /api/v1/tenders` | USER | Создать тендер (-> `ON_REVIEW`) |
| `GET /api/v1/tenders?status=&category=&minPrice=&maxPrice=&deadlineFrom=&deadlineTo=&q=&page=&size=` | все | Каталог (по умолчанию открытые) |
| `GET /api/v1/tenders/my` | USER | Мои тендеры |
| `GET /api/v1/tenders/{id}` | все* | Карточка тендера (+ количество заявок) |
| `PUT /api/v1/tenders/{id}` | владелец | Редактировать (`ON_REVIEW`/`REJECTED`) |
| `POST /api/v1/tenders/{id}/resubmit` | владелец | Повторно на модерацию |
| `POST /api/v1/tenders/{id}/cancel` | владелец | Отменить |
| `POST /api/v1/tenders/{id}/bids` | USER | Подать заявку |
| `GET /api/v1/tenders/{id}/bids/my` | USER | Моя заявка на тендер |
| `GET /api/v1/bids/my` | USER | Мои заявки (с местом после закрытия) |
| `GET /api/v1/tenders/{id}/results` | все* | Рейтинг и победитель (после закрытия) |
| `GET /api/v1/notifications`, `…/unread-count`, `POST …/{id}/read`, `POST …/read-all` | все | Уведомления |
| `GET /api/v1/admin/tenders/review-queue` | ADMIN | Очередь модерации |
| `POST /api/v1/admin/tenders/{id}/approve` · `/reject` · `/cancel` | ADMIN | Модерация |
| `POST /api/v1/admin/tenders/close-expired` | ADMIN | Закрыть просроченные сейчас |
| `GET /api/v1/admin/users`, `POST …/{id}/block`, `POST …/{id}/unblock` | ADMIN | Пользователи |

\* неопубликованный тендер виден только владельцу и администраторам, остальным он отдаёт 404.

Готовый сценарий запросов для IntelliJ HTTP Client / VS Code REST Client - [requests.http](requests.http).

## Структура репозитория

```
common/          общие типы: Actor, ошибки, порты TransactionRunner/EventPublisher, пагинация
users/           пользователи, регистрация, блокировка
tenders/         тендеры, жизненный цикл, модерация
bidding/         заявки, рейтинг, закрытие тендеров, итоги
notifications/   внутренние уведомления по событиям
app/             Spring Boot приложение: security, обработка ошибок, конфигурация, интеграционные тесты
docs/            бизнес-правила
```
